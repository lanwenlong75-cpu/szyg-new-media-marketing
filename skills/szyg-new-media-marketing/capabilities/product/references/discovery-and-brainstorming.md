# 产品探索与头脑风暴

本方法将已接入的PM Skills、Product Discovery和BMAD创意卡用于当前产品；许可及原件见[开源来源](opensource.md)。当前项目约定和用户要求决定范围。原件中的软件开发角色、固定创意数量、英文口令、周期和附带服务推荐均不直接成为本项目要求。

## 先判断这次讨论要推进什么

产品方向不清时，先帮用户解释“谁在什么情境下，想取得什么进展，现在怎样解决，代价是什么”。读当前产品和已知反馈，给出有依据的初步判断。缺少真实用户证据时，把问题表述为待验证机会，不编造用户访谈、市场需求或付费意愿。对话本身可澄清创始人意图、成本和交付，但客户需求仍需行为证据。

已有清楚方案或明确局部修改时直接推进相关交付；不强制每次走全套发散、访谈或评分。把新产品、现有产品的新方向、已验证方案的实现区分开；当前品牌有资料与权益底板，不据此假定所有方向已上线验证。

## 按问题取方法

| 本次需要 | 实际读什么 | 输出应帮助用户作什么决定 |
|---|---|---|
| 现有产品增加或重组价值 | [现有产品多视角创意](../third_party/phuryn-pm-skills/brainstorm-ideas-existing/METHOD.md) | 值得比较的不同方案及取舍 |
| 从零探索新产品 | [新产品创意](../third_party/phuryn-pm-skills/brainstorm-ideas-new/METHOD.md) | 先验证哪类人、场景和价值 |
| 问题、方案、实验混在一起 | [机会方案树](../third_party/phuryn-pm-skills/opportunity-solution-tree/METHOD.md) | 一个目标、机会依据、不同解法及验证 |
| 想法看起来好但风险不明 | [四类假设](../third_party/phuryn-pm-skills/identify-assumptions-existing/METHOD.md)、[优先验证](../third_party/phuryn-pm-skills/prioritize-assumptions/METHOD.md) | 错了会伤害结果且证据薄弱的关键假设 |
| 需要真实用户输入 | [访谈脚本](../third_party/phuryn-pm-skills/interview-script/METHOD.md) | 最近真实经历、替代做法、付出和障碍；不诱导用户夸方案 |
| 需要低成本试验 | [实验设计](../third_party/phuryn-pm-skills/brainstorm-experiments-existing/METHOD.md)、[发现框架](../third_party/alireza-product-discovery/product-discovery/references/discovery-frameworks.md) | 假设、方法、观察指标、预设判断及下一步 |

同一助手可以分别从用户价值、用户体验、交付与成本、技术实现角度审视，不将这些视角写成其他员工已经参与或已同意。用户与资料已给的信息不重复追问；一般一次补一个最有决策价值的问题，同时继续能独立做的分析。

## 让方案产生区别

发散时先保留不同机制，例如交付载体、上手路径、服务强度、目标人群或使用时机的变化。避免只给不同宣传口号、同一功能的小变体，或每个方案都加更多权益。根据复杂度挑少量有区别的方案，比较用户获得的成果、成本与依赖、验证难度、适用情况和放弃什么，给出推荐及可能推翻推荐的证据。

想法陷入同一路径时，按需使用[BMAD原始方法卡](../third_party/bmad-brainstorming/brain-methods.csv)中的一种：

- First Principles Thinking：先问用户真正要完成什么，已有课程和工具是手段还是必须保留的约束。
- Reverse Brainstorming：设想用户会在哪一步失败或离开，再把原因转成可改进的方案。
- Assumption Reversal：挑一条习惯性前提反过来设想，结果仍为假设，不能直接废止已确认权益。
- SCAMPER Method：替代、组合、迁移、调整、另用、删减、反转，寻找不同的交付机制。
- Six Thinking Hats：依次看事实、感受、好处、风险、新方案和下一步；感受与事实分开。

用户不需要先选择框架名或技术菜单。固定数量、讨论时长、重复轮数由实际任务决定，不为凑流程制造内容。需要图示时可画简短机会树或对比图；不是每次强制启动可视化服务。

## 从发散收敛到验证

把机会写为“需要取得的进展”，把方案写为“怎样帮助取得进展”，把假设写为“我们相信但尚未证实的条件”。四类关键假设分别是用户是否要、是否会用、能否持续经营、能否实现/交付。对原文事实、业务方判断、用户观察、分析建议和未知标来源。

先定性判断错误影响、证据强弱、最便宜的检验方法。没有用户规模、转化、时长或成本证据，不补造RICE、ROI或市场规模。需要计算时使用本模块脚本：

```text
python <PRODUCT目录>/scripts/prioritize_assumptions.py --input <假设JSON> --output <结果JSON>
```

输入只接受已有数据、明确注明的分析估计或合成测试。risk/certainty缺失时留null；工具不会自动把未知填成0或1。分数来自输入估计，不是成功概率或真实客户结果。优先级辅助讨论，不能自动否决方案或宣布用户需求得到验证。

选择一个最该验证的假设，准备最小实验：合适的人群与招募条件、实际任务、观察什么、数据如何记录、什么结果继续/修改/停止。样本量、阈值、时限作为待确认建议，测试开始前锁定；小样本用于发现障碍，不宣称有统计结论。客户联系、收款、群发、外部发布和线上试验按实际授权执行，设计实验不等于实施。

## 每轮讨论留下有用结果

对重要讨论记录：当前问题与依据、候选方案及取舍、我的推荐和理由、关键假设、待回答的问题、最小验证、已作/待作决定。用户只改一句时不强制长报告。用户确认方案的具体范围后，才把对应交付改入产品定义和权益清单，再更新海报与私域交接；探索稿不自动成为商业承诺。

讨论价值看是否减少了关键不确定性、促成清楚取舍、减少交付歧义或形成可验证下一步。文件数量、创意数量和助手自评不是效果证明。开源接入后的本次试用可以验证工作流是否跑通，真实客户效果留待实际观察。
