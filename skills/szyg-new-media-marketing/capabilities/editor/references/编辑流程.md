# 公众号编辑流程

## 选题判断

把宽泛主题转成读者正在做的一项决定。例如“AI提高效率”可以缩小到“老板如何挑选第一个值得试的业务环节”。这是编辑提议，不是作者已确认观点。

观察四项依据：读者问题是否具体；当前对象是否有观点或真实材料；内容与已有文章有何新增；本次是否能给出读者可执行的判断或动作。选题不只追工具热度，也不因一个主题热门就承诺经营回报。

用户要选题库时，为每条候选保存读者问题、核心判断、材料入口、待补依据、文章形式与状态。数量按指令；没有数量要求时先给少量差异明显的候选。未经选择不标为“已选”。

## 不同任务的结构选择

| 任务 | 优先判断 | 可用结构 |
|---|---|---|
| 观点文章 | 作者的判断及其成立条件 | 场景或判断 → 依据 → 条件与边界 → 读者动作 |
| 案例文章 | 谁做了什么、结果如何核验 | 业务问题 → 实际过程 → 有证据的结果 → 可借鉴与不可照搬处 |
| 教程文章 | 读者能否照做，环境是否匹配 | 适用场景 → 前提与输入 → 操作 → 验收 → 常见失误 |
| 活动或产品文章 | 权益、价格与行动入口是否真实 | 读者需要 → 真实权益 → 使用或参加条件 → 行动入口 |
| 原稿精修 | 作者原意及最影响阅读的缺陷 | 先查逻辑与依据，再修句段、标题和排版 |

这些结构是选择依据，不是每篇都必须有的栏目。原稿本身有有效叙事时保留它。

## 面向老板的工作默认

当前项目的读者目标是用AI提升业务效率、赚更多钱。把选题落到销售跟进、资料处理、报价、交付、协作等具体工作时，先读取真实材料，再决定哪个环节值得写；这些环节只是可选方向，不是已确认的客户经历。

评价文章价值时问：老板需要做什么决定；投入什么时间、资料和协作；什么可观察结果能说明尝试有效；哪些关键判断仍需负责人承担。不要把购买某工具直接等同于业务改善。

暂定栏目或口吻是编辑建议。没有产品信息时不编产品、价格、报名渠道或二维码。未启用对象文末钩子标准时，读者行动可以是一次自查或一次小范围尝试。当前员工与对象匹配`context.ending_hook_policy`时，默认按[公众号文末钩子](公众号文末钩子.md)接入本篇主题过渡、素材和领取动作，不因上述通用默认而省略。本次明确要求优先。

## 改稿

先判断任务是否限定局部。局部修改保留其他内容；大改记录新增、删减或移动的主要理由。保留可回读的旧稿，不能把所有新表达都说成作者原话。

不虚构“我服务过”“我的客户”“赚了多少”“提升了多少”。真实采访保留说话人、时间戳或段落位置；外部作者观点保留归属。

遇到资料相互矛盾时，把冲突放进审校记录，采用能核验的版本或避开无法确认的断言。重要事实未齐时可先完成提纲和其余段落，清楚标注交付状态。

## 成稿验收

逐段读实际输出，检查每段是否推进主题，标题的具体承诺是否有正文支持，结尾动作是否与观点相连。使用真实素材时再对照原文，防止润色后新增事实或改变结果强度。

用户给出的篇幅、风格、交付格式优先。没有给篇幅时按信息需要控制长度，不将默认长度写成已确认要求。
