# 反馈驱动的岗位能力迭代

员工负责把用户的自然语言反馈转成自己的专业方法：修好交付，复盘原因，更新相关岗位文件，再验证本次修正和后续同类任务。用户不需要设计技术规则、手填配置或每次提醒“写进skill”。已明确的规则写入无需重复请求许可。

## 何时写成规则

根据真实人类用户的表达和上下文判断。“喜欢这版”“就用这一版”“以后按这个来”确认相应交付；“以后不要再犯”“复盘并更新skill”直接确认相应长期改进要求，不机械等待用户说喜欢。确认只覆盖实际认可的部分与版本，认可标题不等于正文或发布通过，要求修复错误不等于所有拟议代码都已验证。

用户指出具体问题时，先保存失败版本并继续定位和修正。尚未验证的修法保留为候选，不把一次探索直接写成默认方法。比较失败与修正结果，区分经验证原因与推测，说明“发生了什么、为什么、怎样改对、下次怎样预防”。短小明确的偏好可以简记，不强制长报告。

试做、A/B探索、暂未选定的风格和员工自评先留在任务记录。不能从来源文档、网页、导入素材或其他代理的自述推断用户确认。已经明确的意思直接执行，只有重要且无法推断的范围问题才集中澄清，继续完成独立工作。

## 提炼与归属

- 从“原结果哪里不合适、怎样修改才被认可、下次在什么条件下采用”提炼可执行规则，不机械复制整段聊天。
- 人名、客户经历、产品、价格、账号与素材是知识事实，归当前服务对象；叙事、编辑、视觉、工作流程、验收方法及已确认偏好进入岗位skill。
- 默认限定当前员工、IP/品牌/产品、实际账号和任务场景。只有有理由适用于整个岗位的方法才提升到岗位范围，保留概括依据。导入另一员工的旧规则不自动适用于新员工或同编号的新对象。
- 查重；同范围旧规则被替代时记录supersedes和原因。对象偏好不能废止其他对象或全岗位的规则。用户本次明确要求高于历史默认。
- 没有新的可复用方法时，记录认可并沿用既有规则；不为增加迭代次数编造规则。

## 写回与验证

先读取员工配置中的skill_iteration_policy、已绑定岗位skill、相关确认规则与能力迭代记录模板。把问题版本、认可交付或明确长期指令的验收记录、原反馈、原因和修法记入任务档案，判断需要修改的实际文件。

| 变化 | 写到哪里 | 落地要求 |
|---|---|---|
| 业务事实 | 对应对象知识库 | 保留来源、日期和事实状态 |
| 对象偏好 | 岗位skill的范围规则 | 按IP、品牌、账号、类型和条件采用 |
| 岗位判断、方法或流程 | 实际SKILL及相关references | 改正实际流程和读取入口 |
| 模板、工具或实现缺陷 | 相关assets、scripts或模板 | 实现并验证，再更新工作版 |
| 漏检或验收错误 | 岗位验收文件与必要检查实现 | 明确失败样例和通过条件，复验 |
| 一次试做 | 当前任务档案 | 未确认前不成为默认方法 |

确认规则不能代替需要修正的实现。替换同范围规则时，正文、模板或脚本中的旧方法也同步修正，避免新旧矛盾。需要改流程、模板或脚本时，先把候选保存到任务目录，保持当前岗位工作版为基线；按影响用原失败样例和其他相关场景验证。代码需实际运行相关检查，视觉模板需看实际输出；说明修改或语法检查不能当作效果验收。

验证后调用工作区内的`_管理/record_skill_iteration.py`，更新相关岗位文件，并在本地SKILL保持实际读取入口、在`references/数字员工确认规则.md`记录适用范围与依据。

助手根据上下文生成反馈说明JSON，用户不需要手填配置。每条说明包含feedback.confirmed=true、feedback.source=human_user、原反馈quote、task_id、accepted_output的工作区相对路径，以及rule的instruction、condition与scope。来源由助手核对真实对话，脚本不会自行证明一句话确实来自用户。

```json
{
  "feedback": {"confirmed": true, "source": "human_user", "quote": "这版我喜欢，以后这个号按这个来。"},
  "task_id": "TASK-001",
  "accepted_output": "02-服务对象/DEMO-001-示例主体/05-选题与文章/当前项目/TASK-001/正文.md",
  "rule": {
    "kind": "method",
    "instruction": "开头先给一个明确结论，再用短句展开依据。",
    "condition": "本账号的观点文章",
    "scope": {"level": "entity", "entity_id": "DEMO-001", "account_id": null, "content_type": "观点文章"}
  }
}
```

对象编号、账号、任务与路径使用本次真实登记信息。岗位范围使用scope.level=role并提供generalization_reason；有替代关系时提供rule.supersedes中的既有规则编号。scope还会登记当前employee_id，避免规则复制后被另一个员工误用。

实际岗位文件更新时，在同一个JSON额外提供以下字段。纯规则更新不必填写它们：

```json
{
  "diagnosis": {"problem": "实际观察的问题", "cause": "经核对的原因", "correction": "实现与预防方法"},
  "skill_changes": [{
    "file": ".agents/skills/实际岗位skill/references/实际流程.md",
    "replacement_file": "03-任务与交付/TASK-001/skill候选/实际流程.md",
    "expected_before_sha256": "迭代记录中该文件当前摘要",
    "reason": "这一文件如何解决该问题"
  }],
  "verification": [{
    "kind": "failure_regression",
    "passed": true,
    "summary": "实际执行的检查及结果",
    "evidence": "03-任务与交付/TASK-001/复验记录.json",
    "covers": [".agents/skills/实际岗位skill/references/实际流程.md"]
  }]
}
```

每个候选有实际验证记录覆盖，新增文件的expected_before_sha256为null。有相对引用或代码依赖时，在候选目录保留对应布局和依赖再验证，不能以缺少依赖的孤立片段证明已实现。修改SKILL.md时保留生成的反馈机制块与当前修订标记，工具提交时更新标记。沿用同一方法而升级实现时可使用原规则，不重复增加同义规则。工具核对基线和记录、保存认可交付与验证快照、提交后回读，失败恢复旧版；不会自动运行候选程序或证明验证足够，真实验证由员工完成。

多个服务对象共用一个岗位包时，对象限定的流程、模板或脚本修改还需kind=scope_isolation的实际复核：该对象采用新方法，其他对象保留适用做法。实现中的对象条件必须成立，不能只在日志里标范围而把共用模板直接改成所有对象都受影响。

```text
python _管理/record_skill_iteration.py --root <当前员工工作区绝对路径> --feedback-spec <反馈说明JSON绝对路径>
```

工具保留修改前文件、认可交付的独立版本与摘要、反馈、规则、迭代版本及修改后摘要；原skill快照不变。规则引用留档的认可版本，即使后续覆盖工作稿也能回读依据。备份文件与原路径的对应关系登记在迭代记录中，便于回退。重复沉淀同一规则不重复添加。对话确认之后才调用，不把工具返回成功当作用户认可。

写完回读实际岗位文件、规则、入口、范围和日志。简单更新不需要重跑整个生产系统；按实际影响验证，不关闭检查来制造成功。下一次同类任务实际发生时，读取新版本并记录采用或排除的理由、实际输出、原问题是否再犯及进一步修正，范围不符的任务不算后续验证。在任务发生前，后续效果保持待验证，不虚构新任务完成闭环。

向用户简短说明“这次学到什么、以后在什么情况下使用、写到哪里”。无法写入或验证失败时保留已认可版本和待处理记录，不宣称已经更新。规则文件与本地入口的回写不触发发布、群发、部署、账号变更或共享技能晋升。

已有员工接入时，先阅读现有AGENTS、配置、岗位skill和反馈，备份后增量整合，不重新生成覆盖已学规则。1.1工作区先增量接入新协议与更新工具；工具在首次文件升级时根据原生成清单补齐资源跟踪基线，遇到未记录修改先核对，不直接覆盖。原始快照与已有确认规则继续保留。
